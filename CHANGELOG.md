# Changelog

All notable changes to this project are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Added

- Kit tooling: strict TypeScript compiled to `dist/` (built by `prepare`), ESLint with `typescript-eslint` strict and stylistic type-checked rules, Vitest with coverage thresholds of 90% (lines, functions, statements) and 80% (branches).
- `opdk` CLI skeleton: command registry, `--help`, `--version`, `<command> --help`. An unknown command or a failing command exits 1 with a message that names the command and, for an unknown one, points to `opdk --help`; the stack prints only with `OPDK_DEBUG=1`. `bin/opdk.js` is type-checked and prints `✗ opdk: <message>` and exits 1 when the CLI fails to load.
- `opdk.config.mjs` loading with `defineConfig`, unknown top-level keys rejected, and `manifest.json` reading with validation.
- CI on pull requests and pushes to `main` (typecheck, lint, tests, build, pack-and-install smoke), plus a tag check that `vX.Y.Z` matches the `package.json` version.
- `npm run smoke` runs the pack-and-install smoke locally: it builds first, installs the packed tarball into a temp project, calls `npx --no -- opdk` and runs `opdk build` on a tiny fixture plugin.
- Build module: `opdk build` bundles with esbuild for platform `browser` (format `cjs`, the `module.exports` footer, `obsidian`, `electron` and the CodeMirror packages external, minified, target `es2020`), builds CSS, and runs the bundle check. The code comes from Dashy's `build` script and its `assert-bundle.cjs`, `build-css.cjs` and `build-vault.cjs`.
- `opdk assert-bundle [file]` fails when the bundle contains Node-only code (`process`, `node:` imports, `__dirname`, markers of the Node build of `yaml`), the check that would have caught Dashy 1.0.0 on mobile. Skipped for `isDesktopOnly` plugins.
- `opdk build-css` inlines `@import` lines recursively.
- `opdk build --vault [dir] [--watch]` builds an unminified bundle into a dev vault, then rebuilds `styles.css` and copies it and `manifest.json` after every build. `--watch` follows the sources through esbuild and polls (every 300 ms) the CSS entry, every file it imports, and `manifest.json`; imports added or removed while it runs are tracked. `dir` falls back to `VAULT_PLUGIN`. Watch builds once at start, and when a CSS step fails the files it had already read stay polled, so fixing them syncs again; a missing `@import` target is polled too, so creating it syncs. Ctrl+C stops watch cleanly. Editing `opdk.config.mjs` needs a restart of watch.
- `build` section in `opdk.config.mjs`: `entry`, `outfile`, `minify`, `target`, `external`, `loader`, `css`. Defaults match Dashy's release build.
- `esbuild` 0.28.2 as the kit's first runtime dependency, pinned exactly. The plugins already use it, and a plugin installing the kit needs no separate esbuild for `opdk build`.
- `opdk build --vault` logs where the folder came from (`--vault` or `VAULT_PLUGIN`) and refuses, with exit 1 and nothing written, a folder whose `manifest.json` holds another plugin id (`--force` overrides this one), a folder that resolves to the plugin root, a value starting with `~` (nothing expands it) and an empty `--vault ""` / `--vault=`. `--vault=<dir>` is in the usage text, and `--force` is rejected without `--vault`. Dashy's `build-vault.cjs` had no guard, so a `VAULT_PLUGIN` left exported in a shell let one plugin overwrite another in the dev vault.
- Build documentation: `docs/build.md` (what the build does step by step, options tables, example output), a short README block, GIFs recorded with VHS (`npm run docs:media`, needs `vhs` and `ffmpeg`).
- Skill `skills/build/SKILL.md`.
- `CommandContext.onInterrupt` (optional) for long-running commands.
- Coloured CLI output through one reporter (`CommandContext.reporter`): `✓` green for a step that passed, `✗` red for one that failed with its hint indented underneath, `·` dim for progress, `!` yellow for a warning. Failures (and esbuild's messages) go to stderr and the `✓ · !` lines to stdout; with `--vault`, `build had N error(s)` therefore moved to stderr. Colour rules: a non-empty `NO_COLOR` turns it off, `FORCE_COLOR` (anything but `0` and `false`) turns it on even on a pipe or with `TERM=dumb`, `TERM=dumb` turns it off, `GITHUB_ACTIONS=true` turns it on, otherwise it needs a terminal. The symbols stay in plain output. The output format is for people and is not a stable interface to parse: use the exit code.
- Scanner module: `opdk scan` runs the community plugin scanner's own ESLint configuration (a mirror of `eslint-plugin-obsidianmd` 0.5.1, `docs/configuration.md`, taken 2026-11-10), a CSS check (`!important`, `:has`, browser features Chrome 142 lacks, through PostCSS and doiuse) and two source checks over the files git tracks. It exits 1 when a step has a finding: the scanner's ESLint warnings count as findings, advisory `!` lines (`ts-suppression`) do not. Only the ESLint configuration is published upstream; the CSS and manifest checks reproduce findings seen on plugin listings. Output is `file:line  rule  message`, grouped by step through the reporter. The code comes from Dashy's `scorecard-check.cjs` and `scanner.eslint.config.mjs`.
- `obsidian-plugin-dev-kit/eslint` exports `obsidianPlugin({ rootDir, tsconfig, ignores })`, the lint config Snipsy, Dashy and Garmy share, built on `eslint-plugin-obsidianmd`'s `recommended` preset, and `DEFAULT_IGNORES`, the 12 paths it leaves out (what all three plugins leave out, the intersection of their lists; a path only some of them have, such as `site/**` or `src/test/**`, goes in that plugin's `ignores` option), so a config can extend or print them.
- `opdk scan` loads ESLint, `eslint-plugin-obsidianmd`, `typescript-eslint` and `doiuse` only when it runs. Every other command and `opdk --help` start as fast as before and never read `manifest.json` through the plugin.
- `opdk scan` skips tracked symlinks and runs git without the `GIT_*` environment variables, so a hook or worktree session cannot point it at another repository.
- `scan` section in `opdk.config.mjs`: `ignore` (globs). Nothing is ignored by default.
- `opdk scan` warns (`!`, the scan still runs) when the `eslint` package that `eslint-plugin-obsidianmd` resolves is another major than the ESLint that runs, naming both versions and the fix (`"overrides": { "eslint": "$eslint" }` in `package.json`, then `npm install`).
- `manifest.json` reading keeps the optional `description`.
- Dependencies, exact-pinned: `eslint-plugin-obsidianmd` 0.5.1, `typescript-eslint` 8.72.2 (was a devDependency), `postcss` 8.5.32, `doiuse` 6.0.6. Peer dependencies: `eslint` (`^9.19.0 || ^10.0.0`, the intersection of obsidianmd's `>=9.19.0` and typescript-eslint's `^8.57 || ^9 || ^10`, within what the plugins run: 9.39 and 10.14) and `typescript` (`>=4.8.4 <6.1.0`, the peer range of typescript-eslint). A test pins the obsidianmd version the mirrored configuration was diffed against, so a bump forces a re-diff.
- Scanner documentation: `docs/scanner.md`, a short README block, GIFs recorded with VHS, skill `skills/scanner/SKILL.md`. `npm run smoke` runs `opdk scan` on the fixture, clean and with a finding.
- E2E core (`obsidian-plugin-dev-kit/e2e`, electron launch mode only; the docs page comes with the helpers): `createObsidianTest({ seedVault, plugins, data, window, obsidianPath, electronArgs, version, timeouts, staleBuildCheck, sweepAfterHours })` returns `{ test, expect, onlyWhen }`. The test provides the fixtures `win` (the Obsidian window), `app` (the Electron application) and `vault` (path plus resolve, read, write and exists helpers); the internal session fixture is not part of the type and is hidden from reports. Options are checked when `fixtures.ts` is imported, and every error names the option.
- E2E isolation: every test gets a fresh Obsidian on a copy of the seed vault (symlinks resolved), a fresh user-data folder, a generated vault id registered in `obsidian.json` as the last-open vault, the built plugins installed from their `manifest.json` ids (`main.js`, `manifest.json`, `styles.css` when present), `community-plugins.json`, and optionally a `data.json` per plugin. `app.json` gets `settingsPopoutWindow: false` and `alwaysUpdateLinks: true` unless the seed vault sets them. `community-plugins.json` is the union of the ids the seed vault enables and the installed plugins. `OPDK_E2E_VAULT` overrides `seedVault`, `OBSIDIAN_PATH` overrides `obsidianPath`.
- E2E trust dialog: the plugin trust flag (`enable-plugin-<vaultId>` in localStorage) is set by an init script before the vault loads, so the "Trust author and enable plugins" dialog never opens and the kit never clicks it. If it opens anyway, the test fails and says so. Native `alert`, `confirm` and `prompt` dialogs are dismissed.
- E2E readiness: after the window opens the fixture waits (polling every 50 ms, no sleeps) until `app.workspace.layoutReady` is true and, for every installed plugin, `app.plugins.plugins[id]` exists and `app.plugins.loadingPluginId` is no longer that id. Obsidian registers a plugin before it awaits its `onload()`, so a command or settings tab that `onload()` adds after an `await` exists once the fixture resolves. A timeout names the state: "plugin still loading: <id>" (inside `onload()`), "plugin not loaded: <id>" (never started), or "the workspace layout was not ready". Confirmed by the kit's live smoke on Obsidian 1.14.5.
- E2E stale-build guard: a plugin whose `main.js` is older than the newest non-test file under its `src/` is refused, naming both files and the fix. A plugin folder without `src/` is not checked. `staleBuildCheck: false` or `OPDK_E2E_ALLOW_STALE_BUILD=1` turns the check off. The check applies to the plugin in the current directory only: another `plugins` entry (a dependency plugin from a sibling checkout, whose `main.js` is often older than its latest `git pull`) is installed as built unless it sets `{ dir, staleBuildCheck: true }`, and an entry's own value overrides the top-level option. The error names the per-plugin option and the env var. Found in the Garmy trial, where every test failed on Dashy's older build.
- E2E Obsidian version: `version` or `OBSIDIAN_VERSION` (plain `x.y.z`) makes the fixture compare it with the running Obsidian, read with `ipcRenderer.sendSync("version")`. Another version, or a version that cannot be read, fails the test. The running version and the launch mode are attached to every test report as annotations. Differences from Snipsy: its fallback that read the version from the `obsidian.asar` on disk, and its `require("obsidian")` fallback, are not carried over (the second one never worked); they belong in Snipsy's migration notes.
- E2E cleanup: teardown runs also when setup throws at any step. It closes the app (bounded by `timeouts.close`), ends the whole process tree (the process group with SIGTERM then SIGKILL on macOS and Linux; `taskkill /T /F` on Windows, because Playwright starts Electron through `cmd.exe` there), removes the vault and user-data folders with retries, and fails the test naming the path when a folder cannot be removed or a process survives. A setup error and a cleanup error are reported together. The session fixture has its own timeout (launch + ready + 3 * close + 20 s), so the kit's budgets fire before Playwright's test timeout and the cleanup always gets to run.
- E2E launch guard: before anything is created, the fixture checks that the plugin has `electron` and that its binary is downloaded (`path.txt`). If not, the test fails saying Electron downloads its binary on first use (about 100 MB), to run `npx electron --version` once and to cache it in CI, instead of a 45 s launch timeout. Copying the seed vault refuses a symlink loop and a dangling symlink, naming the link and the seed vault.
- E2E leftover sweep: a worker removes `opdk-e2e-*` temp folders older than `sweepAfterHours` (default 2, `false` disables) when it starts, and warns about any it cannot remove. `sweepLeftovers()` is exported for use in a `globalSetup`.
- `defineObsidianConfig(overrides)` is the shared Playwright preset: `testDir` `e2e`, one worker, 60 s test timeout, 10 s `expect` timeout, `forbidOnly` and 1 retry on CI, `list` plus an HTML report (`list` only on CI), and trace, video and screenshot kept on failure. Overrides win, and `expect` and `use` are merged key by key. `onlyWhen("CAPTURE")` skips a spec file unless the variable is `1`.
- E2E trace and video follow `use.trace` and `use.video` of the Playwright config for the Obsidian window (all modes, including the object form), because Playwright's own fixtures do not reach an `_electron` window: the trace is started right after launch and attached as `trace` (`obsidian-trace.zip`), the video is attached as `video`, and a recording that the mode does not keep is deleted. CDP mode (phase 2) will have a trace but no video.
- E2E peer dependencies, both optional, so a plugin without e2e installs neither: `@playwright/test` `^1.62.0` (the oldest Playwright the three plugins run) and `electron` `>=39.0.0`. The kit is developed against Playwright 1.65.0 and Electron 44.10.2.
- Kit e2e smoke: `npm run e2e:smoke` runs `test/e2e-fixture/` (two prebuilt test plugins, a seed vault, four spec files with 39 tests, two of them gated and run only on request: a forced failure (`OPDK_E2E_FORCE_FAIL=1`) and the recording behind the docs GIF (`OPDK_E2E_MEDIA=1`), and a check that the run left no temp folder and no process). It opens real Obsidian windows, so it runs by hand before a release, never in `npm test` or CI. `npm run smoke` also imports `obsidian-plugin-dev-kit/e2e` with Playwright installed only at that step, and fails if a Playwright or Electron package arrives with the kit.
- The e2e code comes from Snipsy's `e2e/fixtures.ts`, `obsidian-version.ts` and `remove-dir.ts` and from Garmy's `e2e-setup.sh`.
- E2E `obsidian` fixture (type `ObsidianHelpers`, exported with its option types): helpers bound to the test's window, for settings, commands, files, the editor, appearance, mobile and fakes. Each helper that waits polls Obsidian's state. The fixed delays are the 15 ms between key presses of `editor().type()` and, inside `scrollThrough`, a 100 ms fallback per step for a window that draws no frames. Every wait has an explicit timeout (Playwright's defaults reach the test timeout, or never end) and a failure names what went wrong and what to do.
- E2E helper timeouts: `timeouts.helpers` in the options sets the budget of each kind of wait in the helpers, validated like the rest of `timeouts`: `settings` (a settings tab to register, default 15000), `metadataCache` (default 45000, below the 60 s test timeout of the preset, so the helper can explain itself before the test is killed), `compose` (5000), `theme` (5000) and `ui` (a dialog, the palette, the editor or a view to appear or go away, 10000). A wait that runs out names the option to raise. The type is `HelperTimeouts`.
- E2E settings helpers: `openSettings(tab?)` takes a plugin id or a core tab id, polls `app.setting.pluginTabs` and `settingTabs` until a tab that is registered late appears (or fails listing the registered ids), opens it in the main window and returns the tab content; `closeSettings()`. From Garmy's `settings.spec.ts` and Snipsy's `ui.openSettings` (`e2e/fixtures.ts`); the kit sets `settingsPopoutWindow: false`, so the popout-window detection of both is not needed. That is a default: a value in the seed vault's `.obsidian/app.json` wins. When Settings then opens in a second window, `openSettings` fails after `timeouts.helpers.ui` with a message that names the seed's `app.json` and the key.
- E2E command helpers: `runCommand(id)` runs `app.commands.executeCommandById` and fails with the close matches for an unknown id, or with the reason for a command whose `checkCallback` declined (checked first, because `executeCommandById` returns true for it); `openCommandPalette()`, `runCommandFromPalette(name)` waits for the entry to be selected before it presses Enter; `press(keys)` maps `Mod` to `ControlOrMeta`. From Snipsy's `ui.openCommandPalette` and `ui.runCommand`.
- E2E file and editor helpers: `openFile(path, { mode })` with `source`, `live` or `preview`, which also forces the mode on a note already open in the tab (where `openFile` ignores it, Garmy's `openInReading` loop); `readingView(path?)`; `editor()` with `type` (key by key, focuses only when needed), `text` (through `getValue()`, since CodeMirror renders only the visible lines), `clear`, `setCursor`, `selection`. From Snipsy's `ui.typeInEditor`, `ui.editorText` and `ui.clearEditor`. The editor is found without the `mod-active` class (Obsidian drops it from the leaf while a modal is open) and waited for before the focus check, so `type()` after a closed modal does not click and move the cursor. Differences: `editor().text()` throws "There is no active editor" where Snipsy's `ui.editorText` returned an empty string, and `clear()` throws the same instead of clicking a missing editor. `openFile` does not collapse the side splits, which Garmy's `openInReading` did; that is a plugin concern, done with a command before `openFile`.
- E2E IME helper: `editor().compose(text, { chunking })` enters text through real composition events (`Input.imeSetComposition`, then `Input.insertText` over a CDP session), by word (default) or by character, and waits for CodeMirror to leave the composition between chunks. From Snipsy's `ime.spec.ts` loop. Differences: `compose()` fails when CodeMirror is still in a composition after a commit and when the document did not change. It always commits, so a test that must leave a composition uncommitted (Snipsy's `ime.spec.ts` lines 70 to 83) still needs a raw CDP session of its own.
- E2E appearance and state helpers: `setTheme({ mode, theme? })`, `waitForMetadataCache()`, `clearNotices()`, `hideProperties()`, `scrollThrough(selector?)` (it stays at the bottom, because the reading view drops sections that leave the viewport). `waitForMetadataCache()` returns at once for a vault with no markdown files. From the capture and film specs of Dashy and Garmy (`changeTheme`, the index wait, notice removal, `propertiesInDocument`, the scroll that draws lazy blocks); the fixed pauses there became state waits.
- E2E mobile helpers: `mobile({ width, height, scale })` sets a phone-sized viewport through CDP `Emulation.setDeviceMetricsOverride` (390 x 844 at scale 2), calls `app.emulateMobile(true)`, accepts only the reload rejection that call causes, waits for every plugin to load again and keeps the size; `desktop()` undoes it. A second `mobile()` with another width loads the window again, because the phone or tablet layout is decided from the viewport at load; the same width does not reload. One verified way instead of the block copied into three specs of Dashy and Garmy. Plugins with `isDesktopOnly: true` do not load on mobile, so the wait fails naming them.
- E2E fake swap: `replace(pluginId, propertyPath, impl, arg?)` (two overloads: a factory that declares a parameter must be given the `arg`) assigns a function at `app.plugins.plugins[id].<path>` on the live plugin instance and returns `{ calls(), restore() }`. `impl` is a factory: it runs once in the page with `arg` (serialisable, as for `page.evaluate`) and returns the replacement, so it can keep state between calls. It is serialised as source text and cannot close over variables of the test (that fails with a ReferenceError naming the variable); what it needs goes through `arg`, as Garmy's `fakeGarmin` took `[days, mode, delayMs]`. `restore()` and `calls()` fail with a clear message after the window was reloaded. It refuses a plugin that is not loaded, a property that does not exist, and a factory that throws or does not return a function. Generalised from Garmy's `fakeGarmin`; failure modes and delays stay in the plugin's own function.
- E2E `obsidian.evaluate(fn, arg?)`: runs `fn(app, arg)` in the page with `app` = `window.app` and returns the result (a promise is awaited), typed with two overloads, as `page.evaluate` is (`evaluate(fn)` and `evaluate(fn, arg)`; a function that declares an `arg` parameter must be given one), so a plugin can annotate `app` with Obsidian's `App` through a type-only import while the kit stays free of the `obsidian` package. `fn` is serialised as source text (no closures, pass values in `arg`), and `arg` and the result must be serialisable. It replaces the `globalThis as unknown as { app }` casts of the Garmy trial.
- E2E launch time: each test carries the annotation `obsidian-launch-ms`, the time from the launch call until the workspace and every plugin are ready. The reporter's test duration leaves launch and teardown out because the session fixture runs with its own timeout, so Playwright counts its time in a separate slot and the reported test duration covers the test body only.
- E2E `reload()`: reloads the window with Obsidian's `app:reload` command and waits like `mobile()` does (marks the old page, waits until it is gone, then waits for every enabled plugin to load again), so a spec no longer races the editor after a reload. It fails naming the command when the Obsidian has none, and with its own message when Obsidian refuses to run it. The command reloads without saving, so text typed right before `reload()` can be lost to Obsidian's save debounce: wait for the file to be written first (`vault.read`); fakes from `replace()` do not survive it.
- E2E docs: the page `docs/e2e.md` (what a test gets, quick start, what happens per test, cleanup, options and env tables, helpers, failure artifacts, `onlyWhen`, migration notes, limits), the agent skill `skills/e2e`, an `e2e/tsconfig.json` and `typecheck` script for the specs, notes on the seed vault path, on installing the kit from GitHub in CI (`git+ssh` in the lockfile) and on durations, and migration steps from the Garmy trial (replace callers of the old setup script, drop plugin folders in the seed vault, `onlyWhen` needs exactly `1`), and `docs/media/e2e.gif`, recorded from a real Obsidian window by the gated spec `test/e2e-fixture/e2e/media.spec.ts` (`OPDK_E2E_MEDIA=1`); `npm run docs:media:e2e` re-records it.
- E2E `timeouts.trace` (default 60000, validated like the other timeouts): stopping the Obsidian trace no longer shares `timeouts.close` (5 s). Writing the trace zip grows with the length of the test, and Garmy's 60 s capture test with many DOM snapshots failed its cleanup although its body passed. A stop that runs out fails naming `timeouts.trace`. The session fixture timeout is now launch + ready + trace + 2 * close + 20 s (was launch + ready + 3 * close + 20 s).
- E2E docs: screenshot size follows the display the Obsidian window opens on (1x or 2x). `mobile({ scale })` sets the page's device scale, but `win.screenshot()` still uses the display's pixel ratio; the docs recommend `win.screenshot({ scale: "css" })` for pictures of a fixed size.
- E2E `obsidian.collapseSidebars()` and `expandSidebars()`: collapse or expand the left and right side panels (`app.workspace.leftSplit` and `rightSplit`) and wait until both report that state, so a note gets the whole window. A helper of its own and not a `readingView` option, because it is about the window layout and also serves source and live mode and screenshots. Dashy's `collapseSidebars` and the split collapse in Garmy's `openInReading` become one call. Verified live on Obsidian 1.14.5.
- E2E docs, from the Dashy trial: the fixture waits for every plugin's `onload()`, not for the plugin's first render, so a spec that slept for a render needs its own wait (the migration notes and the "plugin still loading" sentence say so); `openSettings()` returns the settings content, so page-level `has:` filters and container screenshots go through `win`; a table maps Obsidian's view state to `openFile`'s `mode`; screenshots on a Retina display are 2x, with a clip recipe in CSS pixels in place of `webFrame.setZoomFactor`; in the scanner docs and skill the `overrides` entry for ESLint is the fix for a nested ESLint 9.

### Changed

- `opdk scan` runs the newest scanner layer: `@typescript-eslint/no-unsafe-member-access`, `no-unsafe-assignment`, `no-unsafe-argument`, `no-unsafe-call`, `no-unsafe-return` and the two command-id rules (`no-command-in-command-id`, `no-plugin-id-in-command-id`) are on at `warn`, as the public scorecard reports them. The plugin's root `eslint.config.js` or `.ts` is now linted too, with types (a config that imports untyped helpers gets `no-unsafe-*` findings there). A plugin that scanned clean before can now have findings. `docs/scanner.md` has a section on the differences that remain.

- `opdk --version` (and the first line of `--help`) prints the git commit the kit was built from when it is known, for example `0.0.0 (3613c4f)`, so a plugin that pins a commit can tell builds apart. `npm run build` writes it to `dist/build-info.json` (`scripts/write-build-info.mjs`). It comes from git in a checkout (with `-dirty` after uncommitted changes) and from `scripts/archive-commit` in the `git archive` tarball npm downloads for a GitHub install; with neither, only the version is printed.
- Sizes in the build output are labelled `KiB` instead of `KB`; the number is unchanged (bytes / 1024).
- A missing CSS entry with a root `styles.css` present is a `·` line, not a `!` warning, and in `--vault --watch` it is printed on the first sync only. With no `styles.css` either it stays a `!` and says the plugin ships no stylesheet.
- `engines.node` is `^22.13.0 || >=24` (was `>=22.12`): ESLint 10 and `eslint-plugin-obsidianmd` 0.5.1, which the scan loads, require it. CONTRIBUTING and README say so.

Differences from the scripts the plugins have today, per plugin. Anything not listed behaves as before.

- Dashy (`build`, `assert-bundle.cjs`, `build-css.cjs`, `build-vault.cjs`):
  - A missing `@import` is an error that names the importing file (Dashy printed a warning and left the `@import` in the output), and an import cycle is an error (Dashy overflowed the stack). The warning for `@import` of a URL is gone; URL imports stay in place for the browser.
  - A missing CSS entry makes `opdk build` skip the CSS step and keep `styles.css` (`build-css.cjs` died with ENOENT). `opdk build-css` exits 1 with a message that names the entry.
  - The bundle size line is in KiB with one decimal (`0.6 KiB`), computed from the byte length; Dashy rounded the UTF-16 string length.
  - `--vault` and `--watch` are flags of `opdk build` instead of separate scripts. A vault build prints `built` first and `assets copied` after it, `--watch` survives an initial compile error and recovers when the file is fixed, and with `build.css: false` it copies a `styles.css` from the plugin root if there is one.
- Snipsy (`build`, `scripts/build-css.cjs`, `scripts/build-vault.cjs`):
  - Its `build-css.cjs` is Dashy's file (only the comments differ), so the CSS differences listed for Dashy apply to Snipsy's `npm run build` too.
  - The old script copied the root `styles.css` as is and watched it and `manifest.json` with `watchFile`. The kit rebuilds `styles.css` from `src/styles` on every sync, so a hand edit to the root `styles.css` during `dev:vault` is overwritten.
  - The old `build-vault.cjs` also copied `docs/screens` into the vault. The kit copies only `main.js`, `manifest.json` and `styles.css`, the files Obsidian loads; screenshots in a vault's plugin folder are never read. If a spec needs them, keep them in the seed vault.
  - The release and vault bundles become platform `browser` (the `build` script and `build-vault.cjs` both used `node`). The release `main.js` changes: yaml's browser build replaces its Node build, so smoke-test the migrated Snipsy on a phone. `npm run build` gains the bundle check; today's `main.js` fails it and the kit's build passes it.
  - e2e helpers: an uncommitted preedit (`ime.spec.ts` lines 70 to 83) still needs a raw CDP session, because `editor().compose()` always commits. `editor().text()` throws without an active editor where `ui.editorText` returned an empty string.
- Garmy: `opdk build` gains `--minify` and two `@codemirror` externals (`@codemirror/state`, `@codemirror/view`), and needs `loader: { ".png": "dataurl" }` in `opdk.config.mjs`. Its e2e helpers: `openFile` does not collapse the side splits as `openInReading` did.
- All plugins: `.css` is a `text` loader by default in release and vault builds. Dashy's and Snipsy's vault builds had it; it changes nothing until a plugin imports a `.css` file, and it prevents "No loader is configured for .css". `build.loader` entries merge over it.
- Scanner, differences from the scripts the plugins have today. Anything not listed behaves as before.

### Fixed

- A `playwright test` run with a missing Electron binary now fails once instead of once per test (Dashy: 59 identical failures). The check moved from the session fixture into a global setup that `defineObsidianConfig` registers before a plugin's own `globalSetup`. A fixture-level check cannot do this: Playwright replaces the worker after each failed test and runs the fixture again. A config that does not use `defineObsidianConfig` keeps the per-test check.
- `opdk build --vault --watch` no longer misses an edit to a CSS file that was just imported (or just created, for a missing import): a file whose poller registers after the CSS step read it is compared with what the step read, and synced when it differs.

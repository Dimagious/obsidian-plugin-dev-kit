# Changelog

All notable changes to this project are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Changed

- **Breaking:** `scan.ignore` is removed from the `scan` section of `opdk.config.mjs`, which now has no keys. A skipped file was still on the public scorecard: a plugin that listed `site/**` saw `opdk scan` pass while its scorecard showed 20 CSS warnings from `site/assets`. A config that still has the key fails with `"scan.ignore" was removed` and what to do instead, before any check runs. The scan no longer prints "N skipped by scan.ignore" or stops with "scan.ignore skips all N". To clear a finding, fix it or stop tracking the file.
- `opdk scan` type-checks with TypeScript 6 whatever TypeScript the plugin installs, as the community scanner does. The kit carries it as the dependency `typescript-6` (24 MB) and a `module.registerHooks` resolve hook sends every `typescript` request of the scan process to it, so typescript-eslint and `eslint-plugin-obsidianmd` share one compiler. Before, a plugin on TypeScript 5.9 got 0 for `moment(date).format()` imported from `obsidian`, where the scorecard has `no-unsafe-call`, `no-unsafe-member-access` and `no-unsafe-return`. The `lint` line names the version (`typescript 6.0.3`). On a Node without `module.registerHooks` (before 22.15) the scan runs on the plugin's TypeScript, prints a `!` line when it is older than 6 and names the version it used in the `lint` line. Only `opdk scan` uses TypeScript 6: the plugin's own `tsc`, its lint, `opdk build` and `opdk release check` keep the plugin's TypeScript.
- Files that no tsconfig covers no longer fail the scan. They were linted without type information, and a site script with 36 findings had none of them on its scorecard (which lists the 20 CSS warnings of the same folder). They print as one advisory `!` line per file (`outside-tsconfig`). The inference is from that one scorecard, not confirmed by the scanner's authors; [docs/scanner.md](docs/scanner.md#differences-from-the-public-scorecard) has the evidence and the other explanation.

### Fixed

- `opdk scan` missed `obsidianmd/no-nodejs-modules` and the other Obsidian-runtime rules in `global-setup.*`, `*-global-setup.*`, `test-setup.*`, `setupTests.*` and `*.setup.*` files: the preset exempts them as test files, the scanner's ignore list does not name them. A plugin's `integration/global-setup.ts` with three Node imports had three scorecard warnings and 0 here. The exemption is lifted for those patterns only (inferred from that one scorecard, which shows a `global-setup.ts`); worker files, `test-helpers`, `test-support` and `test-utils` folders, `*.testing.*`, `testUtils*` and tool configs stay exempt, and the files the scanner's own list names stay out.
- `opdk scan` did not see the two warnings a plugin's `eslint.config.js` gets for calling `obsidianPlugin()` from the kit: the scanner installs without building the kit (`prepare` does not run), so the import is unresolved there, and the call and the spread of its result are `no-unsafe-call` and `no-unsafe-assignment`. A script that imports `obsidian-plugin-dev-kit` is now linted as if the package did not resolve, and the two findings say how to fix it: name the config `eslint.config.mjs`, which the scanner ignores (`obsidianPlugin({ rootDir: import.meta.dirname })` works from it). A block `eslint-disable` comment does not work: the plugin's own lint rejects it. [docs/scanner.md](docs/scanner.md#differences-from-the-public-scorecard) has the line. Inferred from one plugin's scorecard and reproduced in a copy of it.
- README: the status line said 0.1.0 is released. It now points at the newest tag instead of naming a version.
- Docs: "Differences from the public scorecard" told a plugin to install `typescript@6.0` to see what the scorecard sees; the scan does that itself now.
- Docs: "Updating the kit" in the README and [docs/ci.md](docs/ci.md#updating-the-kit), and the `/opdk:release` skill, told a plugin on v0.1.0 to run `npx opdk kit upgrade`, which v0.1.0 does not have (`unknown command "kit"`). They now give the one-time `npx -y -p github:Dimagious/obsidian-plugin-dev-kit#v0.2.0 opdk kit upgrade v0.2.0`.

## [0.2.0] - 2026-11-13

### Added

- `obsidian.checkLayout({ root, overflow?, touchTargets?, focusRing? })` and `obsidian.layoutProblems(...)`: layout checks inside a root selector that fail with the list of everything wrong: horizontal overflow, touch targets under 44 px (on by default only in the mobile emulation) and Tab stops without a focus ring (opt in). Each check can be turned off; with every check off, or a root that matches nothing, the call fails instead of passing. The checks measure and do not judge a design: for shots a person looks through use `demo.still(name, { publish: false })` with a name prefix such as `review-`.
  - Overflow checks scroll panes too (`overflow-y: auto` computes `overflow-x: auto`), skips text cut with an ellipsis and visually hidden boxes, and has `overflow: { ignore }` (a selector) for a code block or table that scrolls on purpose.
  - A focus ring is an outline or a box-shadow that focus changes (on the element or its `::before`/`::after`), compared between the focused and the unfocused state because Obsidian gives buttons a resting `box-shadow`. Range and colour inputs ring a vendor pseudo-element that cannot be read as a style, so they are compared as screenshots. Shift is pressed before the walk so a mouse click before it does not hide `:focus-visible`; an element that does not take focus back after the blur fails with its name; `focusRing.ignore` skips elements (Obsidian's palette search field has no ring by design). The walk starts at the first visible, enabled focusable element (`focusRing.from` must be inside the root and take focus), ends when an element repeats (a focus trap), lists identical stops once and cuts each kind of problem at 10 with `(first 10 of N)`. `focusRing: { stayInside: true }` reports the Tab that leaves the root.
  - Exported types: `LayoutCheckOptions`, `LayoutProblem`, `LayoutCheckName`, `OverflowOptions`, `TouchTargetOptions`, `FocusRingOptions`; and `ObsidianTestUse` (the options `test.use` takes besides Playwright's: `seed`).
- Stills can say where `opdk demo` puts them. `demo.still(name, { publish: false })` keeps the PNG in `<outDir>/stills` for another tool and does not copy it; `demo.still(name, { out: "listing" })` copies it to the folder `demo.outputs.listing` names in `opdk.config.mjs`, so the pictures a plugin directory lists are copied to their own folder by `opdk demo`. Pictures that a plugin composes from several screens still need the plugin's own composer, fed by `publish: false` stills. A still that asks for a folder missing from `demo.outputs` fails with the folders there are. Stills recorded without the options are published as before. See [docs/demo.md](docs/demo.md).
- Per-test vault seeding for the e2e fixture: `test.use({ seed: { files, config } })` (file or `describe`) adds notes, `.obsidian/` files and `app.json` keys to that test's vault copy before Obsidian starts, so a spec no longer writes them and calls `obsidian.reload()`. A bad shape or a path outside the vault fails before anything starts. A file that would replace what the kit writes is refused with the key to use instead: `.obsidian/app.json` (use `config`), `.obsidian/community-plugins.json`, `.obsidian/plugins/<id>/data.json` of a plugin in the `data` option and the build files (`main.js`, `manifest.json`, `styles.css`) of an installed plugin; so are the paths `.` and `.obsidian`. `VaultSeed` is exported.
- `AppWithInternals` (and `PluginInstance`, `CommandEntry`, `SettingTabEntry`, `InternalPluginEntry`) exported from `obsidian-plugin-dev-kit/e2e`: Obsidian's internal `app` members that specs reach (`plugins`, `setting`, `commands`, `internalPlugins`, `metadataCache.inProgressTaskCount`, `vault` config), typed narrowly, so a spec does not declare its own. The kit's page scripts use the same types.
- `opdk kit upgrade [vX.Y.Z] [--dry-run]` moves a plugin to a kit release: it finds the latest `vX.Y.Z` tag of the kit's repository with `git ls-remote --tags` (no login), resolves it to its commit, rewrites the tag in `package.json`, runs `npm install` for that one package so the lockfile follows, rewrites every kit `uses: ...@<sha>` line of the `package.json` owner in `.github/workflows` with the new commit and a `# vX.Y.Z` comment, runs the new `kit` release check, and prints the kit's CHANGELOG sections between the old and the new version (read from the tag on GitHub; failing to read them only prints a note). It refuses a dirty tree, puts `package.json` and the lockfile back when npm fails (and says to run `npm ci` if `node_modules` looks off), says so when there is no lockfile and npm does not run, stops `git ls-remote` after 60 seconds and `npm install` after 10 minutes, prints the kit CHANGELOG without terminal escape sequences or control characters (and reads at most 1 MB of it), and never commits or pushes. `--dry-run` prints the changed lines and the changelog and writes nothing; it also works on a dirty tree and outside a git repository.
- `kit` step in `opdk release check`, and so in the CI workflow's `release-check`: the tag in `package.json`, the commit the lockfile resolved the kit to and every `uses: <owner>/obsidian-plugin-dev-kit/.github/workflows/<file>@<sha>` line name one release. No network: the lockfile's `version` stands for the tag, and a `# vX.Y.Z` comment must agree. A workflow pinned to a tag or branch instead of a full commit SHA fails. The failure lists every place with the commit it names and points at `opdk kit upgrade`. A plugin that does not use the kit, or does not call its workflows, passes.
- `opdk release` runs the plugin's `npm test` before it changes anything; a failure stops the release with nothing modified. `--no-test` skips it, and a `package.json` without a `test` script is a warning. [docs/release.md](docs/release.md) shows how to make the tag workflow wait for tests too.
- Docs and the `/opdk:unit` skill: `isolate: false` as an option for jsdom-heavy suites with the proof it needs (one worker, shuffled, several seeds, plus default order on one to three workers), the typical leaks and the three measured outcomes (3x, no gain, 1.8x with failures on one worker); never a default.
- Docs and the `/opdk:unit` skill: type-check tests through a `tsconfig.test.json`, import the plugin from the source file and not through a relative path that lands on the root `main.js` bundle (TS7016 under `strict`, `any` in Vitest), and what the preset's lint ignoring `src/**/*.test.ts` means for test helpers.
- Docs: "Updating the kit" in the README and [docs/ci.md](docs/ci.md#updating-the-kit) (how a plugin learns about a kit release, how to make Dependabot ignore the kit, the command, the check), and `opdk kit upgrade` and the new check in the `/opdk:release` skill.
- Agent skill `/opdk:audit` for a plugin that already uses the kit, with its eval case. Phase 1 reads and measures without changing anything: coverage over all of `src` against the gate, the tests type-checked through a scratch tsconfig, unit runs on one worker in shuffled order before anyone turns `isolate` off, every picture's size, ratio, alt text and maker, a contact sheet per GIF that keeps the last frame, and the plugin's own claims about the kit. Findings carry file:line or a measured value and a triage (KIT, KIT-GENERIC, PLUGIN-ONLY, KNOWN with the number of plugins). The author picks what phase 2 does, one branch per batch, or takes backlog items only. It is distilled from a draft that was run on three plugins.

- `obsidian-plugin-dev-kit/vitest/dom` installs more of Obsidian's DOM helpers, read from the shipped app (1.14.5): `createSvg` (global and on nodes), `detach`, `insertAfter`, `indexOf`, `setChildrenInPlace`, `matchParent`, `getCssPropertyValue`, `isActiveElement`, `toggleVisibility`, `innerWidth`, `innerHeight`, `addEventListeners`, `trigger`, delegated `on` and `off`, the `UIEvent` getters `targetNode`, `win`, `doc` and `instanceOf`, and the globals `fish`, `fishAll`, `ready`, `sleep` and `nextFrame`. The app's extensions to Array, String, Number, Math and Object, `ajax`, and the animation-based `onNodeInserted` and `onWindowMigrated` are not ported; [docs/unit.md](docs/unit.md) lists them.

### Changed

- `opdk release` now refuses, with a `✗` and the way out, when the default branch is ahead of `origin`. It used to print a warning and tag the unpushed commits, which could publish code that CI had never seen. Push them through a pull request, wait for CI, pull, rerun.
- `obsidianPlugin()` turns on one more rule for every plugin that uses it: a bare `window.<member>` (`window.addEventListener`, `window.innerWidth`, `window["x"]`) is an `error` through `no-restricted-syntax`, because it refers to the main window and not to the popout window the code runs in; use `activeWindow`. This is plain Obsidian behaviour that every plugin meets. `window.open` and the timer functions stay allowed. A handler parameter named `window` (the second argument of `workspace.on("window-open")`) is reported too; rename it. The community scanner does not report the rule, so `opdk scan` is unchanged. To opt out, add a block after the preset with `"no-restricted-syntax": "off"`; a plugin that sets `no-restricted-syntax` itself replaces the kit's selector (`BARE_WINDOW_SELECTOR` is exported). `@typescript-eslint/no-require-imports` stays off, like upstream; [docs/scanner.md](docs/scanner.md) shows how to add it and what to do instead for a Node module on mobile.
- `ui/sentence-case` is documented as off on the public scorecard too, with the snippet that turns it on.

### Fixed

- `obsidian.hideProperties()` is saved to `app.json` at once. It set the option in memory only, and Obsidian read `app.json` again after the next settings save (`demo.cleanUi()` does one), so the properties block came back. A spec no longer has to write `app.json` itself. The helper throws on an Obsidian without `vault.setConfig` or `vault.saveConfig`; the setting would not stick there. It saves to `.obsidian/app.json`, so the vault copy of the test changes on disk.
- `opdk e2e`: closing the Obsidian process tree no longer fails with `kill EPERM` when the group had already exited. On macOS a process group whose members have exited but not yet been reaped by the parent answers EPERM to every signal, signal 0 included, until the event loop reaps them. The teardown now treats EPERM as "maybe gone" and keeps polling; it fails only if the group still answers after the SIGTERM and SIGKILL waits, and the error then names EPERM and carries it as the cause.
- Docs and the e2e launch hint told users to fetch the Electron binary with `npx electron --version`, which starts Electron. They now say `node node_modules/electron/install.js` (the command CI uses); the launch error prints the real path of that script, since Electron can be hoisted, also in the e2e migration steps for a fresh checkout and in the `/opdk:e2e` skill.
- `docs/*.md` are in the package now (`files`), so a plugin's skill can link `node_modules/obsidian-plugin-dev-kit/docs/<module>.md`. The GIFs and tapes in `docs/media` stay out of the tarball.
- The skills for build, demo, e2e, release and scanner pointed at `github.com/.../blob/main/docs/*.md`, which can differ from the installed kit. They now name `node_modules/obsidian-plugin-dev-kit/docs/<module>.md`, like the unit skill.
- Docs, e2e: `vault.write` is plain file system access and Obsidian's index learns of the file when its watcher fires, so a spec that writes and then acts through the index polls `obsidian.evaluate((app: App, p) => app.vault.getFileByPath(p) !== null, p)` with `expect.poll` first, and calls `waitForMetadataCache()` after that where links, tags or frontmatter matter (it only loops over files already indexed, so it does not replace the poll). Said next to the `vault` fixture and in the e2e skill.
- Docs, e2e and demo: `settle()` does not see drawing on a canvas (a chart); a still of a canvas needs its own wait (a pixel poll, the chart library's ready flag). Also in the e2e and demo skills.
- Plugin names removed from the JSDoc and comments in `src/`, which ship in the `.d.ts` and `.js` files. One runtime message changed with them: the `beat()` seconds error no longer names a plugin.
- Docs: `opdk scan` reported 0 where the public scorecard flagged `moment(date).format(...)` (`moment` imported from `obsidian`) as `no-unsafe-call`, `-member-access` and `-return`. Reproduced: the cause is `esModuleInterop` (TypeScript 6 forces it on; TypeScript 5 with `esModuleInterop: true` behaves the same), under which the namespace import of an `export =` module such as `moment` is not callable. It is TS2349 in the plugin's own `tsc --noEmit` too. The live scanner very likely runs TypeScript 6 (inferred). [docs/scanner.md](docs/scanner.md) has the version table, how to see it (`typescript@6.0` for the check, which also breaks the plugin's typecheck until the call is fixed) and the plugin-side fix.

## [0.1.0] - 2026-11-12

### Added

- `defineUnitConfig({ obsidian: { node, dom } })`: a stub path for the test files that run in node and `"obsidian-test-mocks"` (or another stub path) for the files in `dom`. Before, `"obsidian-test-mocks"` left the node project with no `obsidian` alias (`Failed to resolve entry for package "obsidian"`), and a plugin had to merge a root alias by hand. The string forms work as before. A missing or non-string `node` or `dom`, an unknown key, and `node: "obsidian-test-mocks"` throw with the option named; `dom: "obsidian-test-mocks"` still needs `dom` globs.
- Docs and the `/opdk:unit` skill: obsidian-test-mocks for UI tests (exact pin, `dom` project only, Dependabot ignoring majors, its peers and its gaps in 8.0.0), the symptoms of a file that needs a DOM (`document is not defined` first), a one-liner that lists the failing files of a `dom: []` run, the `DOM.Iterable` note for type-checked tests, `vite` as a peer that Vitest 5 installs by itself, and `environment`, `coverage.reportsDirectory` and the old polyfill's setup file in the migration steps.
- `defineUnitConfig()` works with a linked kit (`npm link`, `file:`): when the kit's folder is outside the plugin, the preset adds it and the workspace root to `server.fs.allow`, so the `dom` project loads `dist/vitest/dom/setup.js` with `server.fs.strict` on (`Cannot find module '/@fs/...'` before). Copies under `node_modules` usually get no extra entry.
- Docs for the unit-test module: a "Unit tests" block in the README, [docs/unit.md](docs/unit.md) (options, the coverage floor, the `dom` split and how to find the files that need it, the DOM helpers and their two deviations, peer versions, migration notes) and the agent skill `/opdk:unit` with its eval case.
- Unit-test module, phase 1: `defineUnitConfig()` in `obsidian-plugin-dev-kit/vitest` and Obsidian's DOM helpers for jsdom in `obsidian-plugin-dev-kit/vitest/dom`.
  - `defineUnitConfig({ coverage, obsidian, dom, include, rootDir })` returns a plain Vitest config (spread it or `mergeConfig` it). Defaults are what three real plugins use: tests in `src/**/*.test.ts`, node, v8 coverage enabled, reporters `text` and `json-summary` (`coverage.extraReporters` adds `lcov` and `html`), report folder `coverage`, thresholds 90 lines, functions and statements, 80 branches, and `**/*.test.ts`, `src/test/**` and `**/*.d.ts` always excluded from coverage. `coverage.include` is required and the factory throws with an example when it is missing (Vitest 4 and 5 report only imported files otherwise, so an untested file would escape the gate). A threshold below the default is an error unless `coverage.allowLowerThresholds: true` (which must be a boolean; any other value throws and names the option).
  - `obsidian` is a path to the plugin's own stub (resolved from `rootDir`) or `"obsidian-test-mocks"`, which uses that package's `vitest-setup`, aliases `obsidian` to the package's `obsidian` module (the `obsidian` types package has no JavaScript entry) and skips the kit polyfill, all in the `dom` project only (the package is a dependency of the plugin, never of the kit, and needs `dom`).
  - `dom` lists the test files that need a DOM. With globs the config has two Vitest projects: `unit` (node, every other test file) and `dom` (jsdom plus the polyfill setup file). `dom: "all"` runs everything in jsdom; omitted or `[]` runs everything in node. The coverage gate stays at the root, so it counts both projects.
  - `installObsidianDom()` / `uninstallObsidianDom()` (and the setup file `obsidian-plugin-dev-kit/vitest/dom/setup`) install a subset of Obsidian's DOM extensions on jsdom, with the behaviour read from the shipped app (Obsidian 1.14.5). Covered, and nothing else: `createEl`, `createDiv`, `createSpan`, `createFragment` (global, and `createEl`, `createDiv`, `createSpan` on every node), with `cls`, `text` (string or fragment), `attr` (null removes), `title`, `value`, `type`, `placeholder`, `href`, `parent`, `prepend`, `on*` listeners and the callback; `appendText`, `empty`, `instanceOf`, `doc`, `win`, `constructorWin`, `setText`, `getText`, `setAttr`, `setAttrs`, `getAttr`, `addClass`, `addClasses`, `removeClass`, `removeClasses`, `toggleClass`, `hasClass`, `find`, `findAll`, `findAllSelf` (and `find`, `findAll` on fragments), `show`, `hide`, `toggle`, `isShown`, `setCssStyles`, `setCssProps`, `onClickEvent`, `activeWindow`, `activeDocument`. Existing `show`, `hide`, `toggle`, `activeWindow` and `activeDocument` are left alone. Install twice is a no-op, install without a DOM throws with the fix. Two deviations from the app: `isShown` is true for an element that is in the document with no inline `display: none` on itself or an ancestor (the app returns `!!offsetParent`, which jsdom always reports as null), and `scrollIntoView` is a no-op added when jsdom lacks it (the app has no such helper; browsers do). Like the app, `Node#createEl` and its siblings write `parent` into the info object they are given; the global `createEl` does not mutate it.
  - `vitest` (major 5), `@vitest/coverage-v8` (the same version) and `jsdom` (30 or newer, only with a `dom` project) are not declared as peer dependencies: npm checks an optional peer whenever the package is installed, so a plugin on Vitest 3 or jsdom 26 got `ERESOLVE` on `npm install` of the kit even without the unit preset. `defineUnitConfig()` checks the versions the plugin resolves from `rootDir` and throws one error naming each package, the version found, the version needed and the install command. `obsidian` (types only) and `jsdom` are dev dependencies of the kit.
- Reusable CI workflow `.github/workflows/plugin-ci.yml` for plugins that use the kit, with [docs/ci.md](docs/ci.md). One read-only job (`contents: read`, `persist-credentials: false`, every action pinned to a commit SHA): `npm ci`, lint (skipped with a notice when the plugin has no `lint` script), typecheck (`npm run typecheck`, else `tsc --noEmit`), `npm run test`, `opdk scan`, `opdk release check --no-build --no-api`, `npm run build`, then an upload of `main.js`, `manifest.json` and `styles.css` as `<plugin id>-bundle` (the job fails when `main.js` or `manifest.json` is missing). Optional `coverage/**` upload. Inputs are `node-version`, `runs-on` (default `ubuntu-24.04`, not `ubuntu-latest`) and one boolean per step; no input takes a command. Plugin-specific steps stay in a second job of the plugin's `ci.yml`, and concurrency stays in the caller. A test (`src/ci/plugin-ci-workflow.test.ts`, with `yaml` as a dev dependency) checks the pinned SHAs, the permissions and that no `run:` script holds an expression.
- Release module, phase 1 (local): `opdk release check` and `opdk release <patch|minor|major|X.Y.Z> [--dry-run]`. The push flow of phase 2 follows in the next entry.
  - `check` is for CI and for before a release; it exits 1 with one `✗` line and a hint per problem. It checks that:
    - `manifest.json`, `package.json` and `package-lock.json` (both version fields) hold the same `x.y.z` version (no `v`, no pre-release) and equal the tag from `--tag <name>` or from `GITHUB_REF_NAME` when `GITHUB_REF_TYPE=tag`;
    - `versions.json` exists, is an object, maps the current version to the manifest's `minAppVersion` and never lowers `minAppVersion` as versions go up (errors); a key or value that is not a version is only a warning, as in the official action;
    - `manifest.json` follows the rules of the official `obsidianmd/obsidian-workflows` action (v1.2.3, `src/manifest.ts`; its warnings print as `!`), with these differences: `author`, `minAppVersion` and `isDesktopOnly` are required (the action only recommends them); a banned word in the `id` is a warning, in the `name` an error; `helpUrl` is accepted and its URL checked; `authorUrl`, `helpUrl` and `fundingUrl` of the wrong type (an array, a number) are errors; the action's "authorUrl is the plugin's own repository" check is covered by the general warning that `authorUrl` links to a repository;
    - `CHANGELOG.md` has a `## [X.Y.Z]` section with an entry;
    - a production build into temp folders (your `main.js` and `styles.css` are not touched) passes the Node-only bundle check, and the asset set is complete (`main.js`, `manifest.json`, `styles.css` when the plugin has CSS); a warning says so when `scripts.build` (else `build:plugin`, else `compile`, the order the community directory uses to rebuild `main.js`) does not run `opdk build`;
    - the build is reproducible: the working tree is built, then the committed tree (`git archive HEAD` extracted to another temp folder, with the plugin's `node_modules` linked in) is built, and `main.js` and `styles.css` must match byte for byte. That catches inputs git does not hold (an untracked or ignored file: the committed tree does not build) and absolute paths of this machine in the output. It does not compare the Node or esbuild version, lockfile drift or line endings on other operating systems, because the same `node_modules` is used. With uncommitted changes the committed tree is compared and the output says so; outside a git repository, or before the first commit, two builds of the working tree are compared and a warning says that this proves much less. pnpm and Yarn PnP installs fall back to two builds of the working tree too, with a warning naming the layout (their packages cannot be linked into a copy). `git archive` applies `export-ignore`, and Git LFS files are pointer text in it, so a build input tracked by LFS makes the comparison differ. A mismatch names the first differing offset and the likely causes;
    - `obsidianmd/no-unsupported-api` against the manifest's `minAppVersion` (type-aware, needs `npm ci`), over the files esbuild puts into `main.js` (read from its metafile, `node_modules` excluded); a shipped file that no tsconfig covers is an error. Blind spot: the rule reads `@since` tags through the TypeScript program, so it reports nothing when the program does not contain the real `obsidian.d.ts` (for example a tsconfig `paths` entry that points `obsidian` at a stub).
    - `opdk scan` is unchanged. `--no-build` skips the build, asset and reproducibility checks, `--no-reproducible` builds once, `--no-api` skips the API check.
  - `release <patch|minor|major|X.Y.Z>` refuses to start unless the folder is a git repository with a clean tree, on the default branch (from `origin/HEAD`, or `release.defaultBranch`), not behind origin (it runs `git fetch --no-tags origin`, never a push), without the tag locally or on origin, and with entries under `## [Unreleased]`. It sets the version in `package.json`, `package-lock.json` and `manifest.json`, adds the version to `versions.json` (an existing entry is never rewritten; a missing file is created), moves the `[Unreleased]` entries under `## [X.Y.Z] - YYYY-MM-DD` (and updates the compare links of the footer when the file has them), runs the release check on the result, then commits `chore(release): X.Y.Z` and creates the annotated tag `X.Y.Z`. When the check fails, or on Ctrl+C (exit 130), the files are restored, the temp folders are removed and nothing is committed. In the check the committed tree gets the bumped files laid over it, so it matches the commit to come. Then the push flow runs (next entry), or with `--no-push` it stops at the local tag. `--dry-run` runs everything but the commit and the tag, prints the diff and restores the files.
  - `release` section in `opdk.config.mjs`: `changelog` (default `CHANGELOG.md`) and `defaultBranch`.
- Release module, phase 2 (the push flow and the reusable workflow):
  - `opdk release <bump>` now continues after the tag, and `opdk release publish [X.Y.Z]` starts the same flow from an existing local tag, for a run that was interrupted or stopped midway (every step checks what is already done). `publish` without a version uses the version in `manifest.json`. It needs the GitHub CLI signed in with write access to the repository `origin` points at; this is checked before anything is bumped (`--no-push` skips it and stops at the local tag, and so does `--dry-run`, which never reaches GitHub). The steps:
    - push only the tag (`git push origin refs/tags/X.Y.Z`; no force flag exists in the code, and a tag on origin that points elsewhere stops the flow), not the branch;
    - find and wait for the kit's release run of that tag: the push run on exactly the tagged commit and the tag (`head_branch`, so a second tag on the same commit does not mix runs) whose `referenced_workflows` include the kit's `release.yml`, read with `gh api repos/<repo>/actions/runs?head_sha=<commit>&event=push` (a Pages or any other workflow that also runs on the tag push is never waited for). If none shows up within 3 minutes the message says that the plugin's tag workflow must call the kit's `release.yml`. The wait is 20 minutes by default (`--timeout <minutes>`), with a progress line whenever the state changes; when the run fails, is cancelled or times out, print the run URL and stop: the tag stays, and the hint says to release a new patch version, or to delete a draft the failed run left behind, re-run the jobs on GitHub and resume;
    - check the draft release: it is a draft, holds `main.js`, `manifest.json` and `styles.css` only if the plugin has CSS (`--zip` also expects `<id>-<version>.zip`) and nothing else; the draft's notes must equal the `## [X.Y.Z]` section of the CHANGELOG as committed at the tag (trailing whitespace aside), or the flow stops; download the assets and compare them byte for byte with a build of the tagged commit made on your machine (`git archive` of the tag, the committed-tree build of the reproducibility check, i.e. `opdk build`, so the plugin's build script must run `opdk build`, or the comparison fails after the tag is already pushed) and with the committed `manifest.json`; the zip, when expected, is checked for presence and size only; run `gh attestation verify` for each attested file against the repository, the tag ref, the tagged commit and the signer: the certificate identity must match `^https://github\.com/Dimagious/obsidian-plugin-dev-kit/\.github/workflows/release\.yml@`, i.e. the attestation is signed by the kit's `release.yml` at any ref, so call that workflow, do not copy it. Every page of the release list is read, and two releases for one tag stop the flow;
    - publish it (`gh release edit X.Y.Z --draft=false --latest`) and confirm it is public and GitHub's latest release;
    - push the release commit to the default branch (`git push origin <release commit>:refs/heads/<default branch>`, no force; later local commits stay local, and nothing is pushed when origin already holds the commit). When origin rejects it, the release is already public: the message says so and how to merge origin's commits without rewriting the release commit;
    - print the release and run URLs.
  - Every stop, and Ctrl+C (exit 130, the temp folders are removed), prints where it stopped, what is on origin and the command to resume: `opdk release publish X.Y.Z`. A stop whose own hint says to release a new version (a draft that does not match the tag, a tag on origin that points elsewhere) prints `opdk release patch` instead of the resume line, because resuming would stop at the same place. A release that was already public never gets "delete the draft": the message says it is public and not to delete it. `gh` and `git` are run with argument arrays; git gets `GIT_TERMINAL_PROMPT=0` and, unless `GIT_SSH_COMMAND`, `GIT_SSH` or `core.sshCommand` is set, `GIT_SSH_COMMAND="ssh -o BatchMode=yes"`, and `gh` gets `GH_PROMPT_DISABLED=1`, so nothing waits for a prompt.
  - `opdk release notes [X.Y.Z]` prints the body of the `## [X.Y.Z]` section of the changelog (the manifest version by default); the workflow uses it for the release notes.
  - Reusable workflow `.github/workflows/release.yml` (`on: workflow_call`, inputs `node-version`, default `22`, and `zip`, default `false`). The plugin calls it from a workflow of its own, which must grant the same permissions:

    ```yaml
    name: Release
    on:
      push:
        tags: ['*.*.*']
    permissions:
      contents: write
      id-token: write
      attestations: write
    jobs:
      release:
        uses: Dimagious/obsidian-plugin-dev-kit/.github/workflows/release.yml@<full commit SHA of the kit release>
    ```

    Two jobs. `build` (permissions `contents: read`, nothing else) checks out the full history, refuses the tag unless it equals the `manifest.json` version and `origin/<default branch>` is an ancestor of the tagged commit (the branch is pushed after the release, so the release commit is ahead of it by design), runs `npm ci` (no npm cache), `opdk release check --tag`, the plugin's build script (the first of `build`, `build:plugin`, `compile`, as the community directory does; it must run `opdk build`, because `opdk release` compares the assets with its own `opdk build` of the tag), and hands `main.js`, `manifest.json`, `styles.css` (when present) and the release notes over as a workflow artifact. `release` (permissions `contents: write`, `id-token: write`, `attestations: write`) needs `build`, checks out nothing and runs no npm and no plugin code: it refuses any file in the artifact it does not expect, attests `main.js`, `manifest.json` and `styles.css` with `actions/attest-build-provenance`, optionally zips them (`zip: true`), and creates a draft release named after the tag with the changelog section as notes. It never publishes. The attestations are signed by the kit's `release.yml`, whichever job runs them. Every third-party action is pinned to a full commit SHA with its version in a comment, and so should the plugin pin the kit: `uses: Dimagious/obsidian-plugin-dev-kit/.github/workflows/release.yml@<full commit SHA of the kit>`. The plugin needs `opdk` and `scripts.build` in its `package.json`, and Actions workflow permissions that allow the caller's `permissions` block.

- E2E `reload()`: reloads the window with Obsidian's `app:reload` command and waits like `mobile()` does (marks the old page, waits until it is gone, then waits for every enabled plugin to load again), so a spec no longer races the editor after a reload. ### Fixed

- `opdk release check` now reports a `package.json`, `package-lock.json`, `manifest.json` or `versions.json` that `JSON.stringify` would not write back unchanged (a one-line `versions.json`, hand-aligned values, mixed line endings) as an error, in the `versions` or `versions.json` group. Before, the check passed and `opdk release <bump>` refused the file on release day. The hint is a `node -e` command that rewrites the file with its own indent; Prettier is no fix, it keeps a one-entry object on one line.
- A tag that is the manifest version with a `v` prefix is reported as `tag "v1.7.2" does not match manifest.json version 1.7.2: Obsidian release tags have no "v" prefix.`, in `opdk release check` and in the reusable release workflow.
- Release docs, "Migrating": the `ci.yml` and `package.json` changes are generic (`release check --no-build --no-api` in branch CI, no zip step, which `release:*` scripts go), and the `versions.json` example is in the format the kit writes.
- `demo.film().shot()` and `demo.still()` after a plain `win.screenshot()` in the same test: the next shot failed with "The window did not become ... at scale 2" (found in a trial on a plugin, reproduced here on a 1x external display). Playwright's screenshot drops the device metrics override from the page, while the kit's session still counted its last override as active, and Chromium ignores a set that repeats it. `mobile()`, `desktop()` and the demo now send the override through one tracker that clears the session's override first when a set would repeat the last one. A phone film also takes the phone size from what the session last set, not from what the page reports after the drop, so the next phone shot comes back at the phone size and the film's scale, and a second `obsidian.mobile()` after a plain screenshot restores the phone size. A second identical `obsidian.mobile()` in the same test now clears the override before setting it (the window briefly takes its own size; nothing reloads). The CDP calls are unchanged in every other case.
- A `playwright test` run with a missing Electron binary now fails once instead of once per test (59 identical failures in one plugin). The check moved from the session fixture into a global setup that `defineObsidianConfig` registers before a plugin's own `globalSetup`. A fixture-level check cannot do this: Playwright replaces the worker after each failed test and runs the fixture again. A config that does not use `defineObsidianConfig` keeps the per-test check.
- `opdk build --vault --watch` no longer misses an edit to a CSS file that was just imported (or just created, for a missing import): a file whose poller registers after the CSS step read it is compared with what the step read, and synced when it differs.
- `opdk demo` loop check: pixels whose channels differ by 8 of 255 or less count as equal, so noise nobody sees no longer warns. A trial film differed in 0.9% of the pixels by one shade and looked identical. A real change still reports its box and share of the pixels.
- `opdk demo` stale-media check names only files `opdk demo` itself wrote earlier (recorded in `<outDir>/published.json`) whose film is gone. It no longer lists every other picture in the output folder (30 files in one plugin, 12 in another). With no record yet there is no warning; a deleted file drops out of the record. It also names recorded files of a film that still exists, encoded cleanly in that run and did not write them (an output turned off with `mp4: false`, or moved with `demo.output`), in a separate warning.
